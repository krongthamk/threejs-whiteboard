## Thai support after review and features

Open requested scope: support Thai content throughout the same text paths (plain/sticky/shape/import/display names/people/mentions) and canvas/native editing/PNG/SVG/PDF. Translation of application chrome is not specified by the inherited task; root should use the actual user wording when deciding localization scope.

Baseline evidence: `text-layout.ts` ships only Inter, IBM Plex Mono, Noto Sans JP; unsupported glyph widths fall back to one em; renderer has a single globally configured fallback font; CSS/editor and SVG/PDF embed the same three families; font metrics and PDF coverage generators hardcode those families. A font download alone is insufficient. Add a licensed local Thai family (record OFL/license/version/provenance), matching WOFF/TTF assets, generated glyph/shaping metrics/coverage and fallback resolution in model/renderer/editor/export, preserving Latin/JP layouts. Thai combining marks and words without spaces require grapheme-safe caret/layout/wrap and the same shaping/positioning across output formats; finding 34/55 and F1/F4 introduce the shared paths to extend.

Required evidence: Thai consonants/vowels/tone marks/dotted marks, spaces and no-space sentences, Thai+Latin+JP mixtures, wrap boundaries, caret/selection/backspace, IME composition, shape vertical alignment, clipboard/reload/convergence, name chips/mentions, PNG1x2x/SVG/PDF glyph/position/ink/text extraction parity; offline local font loading and no missing-font warning for supported Thai. Retain existing Latin/JP regression snapshots. Record any renderer/font parser limitation honestly; do not claim support based only on browser editor fallback.
